# 평가 계획

_2026-09-22_

## 두 종류의 평가를 구분한다

혼동하기 쉬운 지점이다. 목적도 방법도 다르다.

| | 평가 A — 모델 성능 | 평가 B — 시스템 검증 |
|---|---|---|
| 대상 | Stage 2 (시계열 분류기) | 전체 파이프라인 |
| 입력 | 이미 추출된 키포인트 `.npy` | **영상 원본** |
| 측정 | 분류 성능 (Recall/FPR) | 실제 동작 · 오류 사례 |
| 용도 | 모델 선택, 논문 표 | 서비스 타당성, 논문 정성 분석 |
| 지금 가능 | **가능** | 영상이 있어야 가능 |

STEP 1~4 는 전부 **평가 A** 다. 평가 B 는 그 뒤에 별도로 한다.

## 평가 A — 모델 성능 (STEP 1~4)

키포인트가 이미 있으므로 바로 가능하다.

### 지표

낙상 감지는 **Recall 우선**이다. 놓치면 사람이 다치고, 오탐은 확인하면 된다.
다만 오탐이 잦으면 알림을 무시하게 되므로(alarm fatigue) FPR 을 함께 본다.

```
                예측
            fall    나머지
실제 fall    TP       FN     ← FN 이 "놓친 낙상". 가장 위험
   나머지    FP       TN     ← FP 가 "헛알림"

Recall    = TP/(TP+FN)   놓치지 않는 비율   ★ 최우선
FPR       = FP/(FP+TN)   헛알림 비율        ★ 함께 봄
Precision = TP/(TP+FP)
F1        = 조화평균
```

3클래스(normal/fall/fallen)이므로 **클래스별로 각각** 낸다.
특히 `fallen` 의 Recall 이 중요하다 — 넘어져 방치된 상태를 놓치면 안 된다.

### Confusion matrix 에서 확인할 것

3×3 행렬에서 **어떤 혼동이 일어나는가**가 수치보다 중요하다.

| 혼동 | 의미 | 심각도 |
|---|---|---|
| fall → normal | 낙상을 놓침 | **치명적** |
| fallen → normal | 방치 상태를 놓침 | **치명적** |
| normal → fall | 헛알림 | 보통 (경보 피로) |
| fall ↔ fallen | 낙상과 낙상후를 혼동 | 낮음 (둘 다 위험 판정) |

마지막이 중요하다. fall 과 fallen 을 서로 헷갈려도 **"위험" 판정 자체는 맞다**.
그래서 이진(위험/정상) 기준 지표도 함께 낸다.

### 추가로 낼 것

| 항목 | 이유 |
|---|---|
| 파라미터 수 | 경량성 — AI Hub 997,200차원 대비 강조점 |
| 추론 시간 (클립당 ms) | 실시간 가능 여부 |
| 5-fold 표준편차 | 19명 규모에서는 분산이 평균만큼 중요 |
| fold 별 개별 수치 | fold3(101클립)이 튀는지 확인 |

## 평가 B — 시스템 검증 (영상 입력)

**목적**: "실제 영상을 넣으면 어떻게 나오는가" 를 눈으로 확인하고 정리한다.
숫자만으로는 알 수 없는 것 — 어떤 장면에서 왜 틀렸는지 — 을 본다.

### 무엇을 만드는가

AI Hub 베이스라인 평가 때 만든 것과 같은 형태의 보고서다
([scripts/make_report.py](../scripts/make_report.py) 재사용).

```
영상별 카드:
  ┌──────────────────────────────────────────┐
  │ clip_0042   [실제 fall] [예측 fall ✓]     │
  │ ┌────┬────┬────┬────┬────┐               │
  │ │0.0s│0.5s│1.0s│1.5s│2.0s│ ← 시간순 프레임 │
  │ └────┴────┴────┴────┴────┘               │
  │ normal 0.05  fall 0.88  fallen 0.07      │
  └──────────────────────────────────────────┘
```

오답은 빨간 테두리로 구분한다. **틀린 사례를 모아 보면 패턴이 보인다** —
특정 자세, 특정 조명, 특정 각도에서 실패하는지.

### 영상 출처 — 세 선택지

#### B-1. OmniFall 테스트셋 (지금 가능) ★

이미 확보한 영상이다. STEP 2 의 test fold 클립을 그대로 쓴다.

- 장점: **지금 바로 가능**, 정답 라벨이 있어 TP/FN 계산됨
- 단점: 학습에 쓴 것과 같은 데이터셋 계열

#### B-2. AI Hub Validation (영상 확보 필요)

**이것이 원래 하려던 것이다.** 문제가 하나 있다.

| 필요 | 상태 |
|---|---|
| AI Hub **라벨** | **로컬 확보** — `data/VL` 에 JSON 27,265개 |
| AI Hub **영상** (VS.zip 55GB) | **미확보** — 해외 IP 차단으로 다운로드 실패 |

라벨에는 `fall_start_frame` / `fall_end_frame` 이 프레임 단위로 있어
평가 기준으로는 이상적이다. 하지만 **영상이 없으면 예측을 만들 수 없다**.

영상 확보 경로:
- GCP 서울 VM (한국 IP + 대용량 디스크) — 신규 크레딧이면 무료
- 교내 서버 / 연구실 PC
- 맥북 스트리밍 재시도 (이전에 세 번 실패)

**이것이 성사되면 가장 강력한 평가가 된다** — AI Hub 공식 모델(RandomForest,
카메라별 8개)과 **완전히 같은 데이터로 직접 비교**할 수 있다.
베이스라인 수치는 이미 측정해 뒀다 (FNF Recall 83.3%, FPR 12.5%).

#### B-3. 직접 촬영 (선택)

실제 설치 환경에 가장 가깝다. 다만 낙상을 안전하게 연출해야 하고
정답 라벨을 직접 붙여야 한다. 시간이 있으면 소규모로.

### 어느 것을 먼저 하는가

```
STEP 1~4 (평가 A)  →  B-1 로 시스템 검증  →  영상 확보되면 B-2 추가
   지금 가능            지금 가능              인프라 필요
```

B-1 만으로도 "영상을 넣으면 이렇게 나온다" 는 보고서가 나온다.
B-2 는 논문의 핵심 비교표를 채우는 것이므로, 영상 확보를 별도 과제로 추진한다.

## AI Hub 비교표 (B-2 성사 시)

같은 데이터·같은 지표로 채운다. 베이스라인은 이미 측정 완료.

| 방법 | 입력 차원 | 시간 모델링 | 카메라 독립 | Recall | FPR |
|---|---|---|---|---|---|
| AI Hub RF (영상) | 997,200 | ✗ flatten | ✗ 모델 8개 | **0.833** | **0.125** |
| 제안: YOLO-pose + 규칙 | 34/프레임 | 윈도우 | ✓ | | |
| 제안: YOLO-pose + LSTM | 20,400 | ✓ 순차 | ✓ | | |
| 제안: YOLO-pose + ST-GCN | 20,400 | ✓ 시공간 | ✓ | | |

베이스라인 수치의 한계: 샘플이 4장면(카메라 8대 = 32영상)뿐이었다.
VS.zip 을 확보하면 베이스라인도 다시 측정해야 공정한 비교가 된다.
