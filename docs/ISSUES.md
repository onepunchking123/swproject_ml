## 1. 위험 상태 전이가 흔들리면 타이머가 리셋된다

### 관찰
`00003` 영상 상태 타임라인 (0.5초 간격):

```
290f fall(0.74) → 319f fall(0.92) → 348f normal(0.50/0.44) → 377f fall(0.82) → 406f~ fallen(0.91)
```

348f 에서 위험 확률이 0.44 로 내려가 한 판정 동안 `normal` 이 됐다. 현재는 히스테리시스(해제 0.35)로
상태를 유지해 넘어갔지만, **0.34 였다면 상태가 `normal` 로 바뀌고 R1 타이머가 0 으로 리셋**된다.
비낙상 `00047` 에서는 실제로 `fall(116f) → fallen(174f) → normal(232f)` 로 2초 만에 빠져나갔다.

### 왜 문제인가
R1(낙상 후 방치)은 "위험 상태가 `t_fallen` 초 **연속**" 이다. 실제 낙상자가 바닥에서 조금 움직이거나
모델 확률이 한 번 흔들리면 타이머가 처음부터 다시 돈다 → **정말 위험한 long-lie 를 놓칠 수 있다.**
반대로 너무 관대하게 잡으면 침대에서 뒤척이는 것도 CRITICAL 이 된다.

### 선택지
| 방식 | 내용 | 장단 |
|---|---|---|
| A. 유예 시간 | 위험 상태를 벗어나도 ≤ 1초면 타이머 유지 | 단순. 유예 길이가 또 하나의 임계값 |
| **B. 비율 기준** | "최근 N초 중 위험 상태 비율 ≥ 80%" 면 발화 | 흔들림에 강건. 연속 조건보다 자연스럽다 |
| C. 확률 누적 | 위험 확률의 이동 평균 ≥ 임계 | 모델 출력을 직접 쓴다. 히스테리시스와 중복 |
| D. 상태 머신 강화 | `fall → fallen → recovering(일어남 감지) → normal` 명시 전이. `stand_up` 이 보여야만 해제 | 가장 정확. `stand_up` 라벨(141개)로 회복 감지 모델 필요 |

**B 는 지금 바로 시험할 수 있다** — `runs/demo/*.jsonl` 에 0.5초 간격 상태가 남아 있어 YOLO 를 다시 돌리지 않고
규칙만 바꿔 재생(replay)하면 된다.

### 팀 결정
- 연속 조건을 유지할지, 비율 조건으로 갈지
- D 로 갈 경우 "일어남" 감지를 별도 학습할지

## 2. `t_fallen` 을 몇 초로 잡을지 근거가 없다

### 관찰
- 데모 기본값 **3초**는 AI Hub 클립이 낙상 후 4.7초밖에 남지 않아서 정한 값이다. 의미 있는 값이 아니다.
- 학습 데이터 클립 길이 중앙값 **1.9초**, 최대 9.9초. 평가 영상은 10초.
- **5초를 넘는 지속 시간은 어떤 데이터로도 검증할 수 없다.**

### 왜 문제인가
임상에서 long-lie 는 보통 **1시간 이상** 바닥에 있는 것을 말하지만, 서비스는 그보다 훨씬 일찍 알려야 한다.
그런데 몇 초가 적절한지는 **오경보 비용과 대응 지연의 트레이드오프**라 데이터가 아니라 서비스 정의의 문제다.

| `t_fallen` | 놓칠 위험 | 오경보 | 비고 |
|---|---|---|---|
| 3초 | 거의 없음 | 침대에 눕기만 해도 울림 | 데모 전용 |
| 30초 | 낮음 | 낮잠·기절 구분 못함 | 1차 확인(보호자 앱 알림) 수준 |
| 5분 | 중간 | 낮음 | 2차(전화·방문) 수준 |
| 30분+ | 높음 | 매우 낮음 | 의학적 long-lie |

### 선택지
- **다단계 알림**: 30초 → 앱 "확인해 주세요" · 3분 → 전화 · 10분 → 응급. 한 값에 모든 걸 걸지 않는다.
- 낙상 이벤트(`FALL`) 직후의 `fallen` 은 짧게, 낙상 없이 시작된 `fallen`(처음부터 누워 있음)은 길게 — **선행 낙상 유무로 임계를 달리** 한다.
- 시간대 가중: 새벽 침실 `fallen` 은 수면일 확률이 높다.

### 팀 결정
- 알림 단계와 각 단계의 시간. **이건 모델이 아니라 제품 결정이다.**
- 검증하려면 **긴 정상 영상**(수 시간, 낙상 없음)이 반드시 필요하다 → 4번·8번과 연결

## 3. 사람이 가려지거나 화면을 벗어나면 판정이 멈춘다

### 관찰
- 빈 입력(사람 미검출)에 모델이 **`fallen` 0.79** 를 낸다 → 검출률 < 50% 윈도우는 `no_person` 으로 막아 뒀다.
- AI Hub 베이스라인 실측: C2 카메라는 침대에 가려 사람이 거의 안 보였고 판정이 뒤집혔다(0.23).
- 현재 `no_person` 이 되면 R1 타이머도 리셋된다.

### 왜 문제인가
**실제 낙상은 가림과 함께 온다.** 침대 옆으로 떨어지면 침대에 가려지고, 카메라 사각으로 굴러간다.
지금 로직은 "안 보임 = 판정 없음" 인데, 서비스에서 "낙상 직후 사라짐" 은 오히려 **가장 의심스러운 신호**다.

### 선택지
- `FALL` 후 N초 내 `no_person` → `FALL_THEN_LOST` 이벤트 (별도 WARNING)
- 검출률 임계를 50% → 30% 로 낮추고, 부분 가림에서도 보이는 관절만으로 판정 (conf 마스킹 — 모델 재학습 필요)
- 카메라 설치 가이드: 침대·소파가 사각을 만들지 않는 위치. 모델로 해결할 문제가 아닐 수 있다.

### 팀 결정
- "사라짐" 을 이벤트로 다룰지
- 설치 가이드를 제품 요건에 넣을지

## 4. `lying` 데이터가 1.9% — 정상적으로 누우면 낙상으로 본다

### 관찰
| 지표 | 값 |
|---|---|
| 학습 데이터 `lying` | **23 / 1,194 (1.9%)**, `lie_down` 22 |
| OmniFall test 의 `lying` 3건 | **3/3 오판** (fall 0.47 / fall 0.40 / fallen 0.92) |
| AI Hub 비낙상 영상 8개 (침대에 엎드림) | 영상 단위 FPR **0.750** |
| 원인 장면 | 피험자가 침대에 엎드려 상체를 숙임 — 몸통 수평도 2.55 |

모델이 "몸통이 수평 = 위험" 으로 학습됐다. OmniFall 논문도 같은 현상을 보고한다 —
*"zero-shot 모델은 fallen 과 lying 을 계속 혼동한다"*.

### 왜 문제인가
**노인 모니터링의 대부분 시간은 앉아 있거나 누워 있는 시간이다.** 이 클래스가 약하면 하루에 수십 번 울린다.
다만 지속 시간 규칙이 순간 오판을 걸러내는 것은 확인됐다 — 00047 에서 FALL 오탐은 났지만 CRITICAL 은 0건.

### 선택지
| 방식 | 내용 | 상태 |
|---|---|---|
| **A. 합성 데이터** | OF-Synthetic `lying` 1,200개 (53배 보강). 논문이 제시한 해결책 | Drive 에 9GB 확보. **AV1 코덱 → ffmpeg 변환 필요.** Colab 세션 회수 8회로 추출 미완 |
| B. FallVision | 침대/의자/서있기 낙상 구분 58명 | Drive 16GB 확보, 미사용 |
| C. 위치 맥락 | 침대·소파 ROI 안의 수평 자세는 감점 | 설치 시 ROI 지정 필요. 규칙으로 즉시 가능 |
| D. 자세 전이 | "서 있다가 갑자기 누움" vs "처음부터 누워 있음" 구분 | 낙상은 전이, lying 은 상태. 모델 입력에 진입 속도 추가 |

A 는 **데이터를 늘려도 모델이 침대라는 맥락을 배우진 못한다** — 합성 lying 이 바닥에 누운 것이면 오히려 fallen 과 더 헷갈린다. C·D 와 함께 가야 한다.

### 팀 결정
- 데이터 확장을 어디서 돌릴지 (Colab 은 8회 실패 · GCP · 교내 서버 · 로컬 M3 밤샘)
- ROI 지정을 설치 절차에 넣을 수 있는지 (사용자 부담)

## 5. 한국 노인 가정의 좌식·바닥 생활이 학습 데이터에 없다

### 관찰
학습 데이터 3종(GMDCSA24·edf·caucafall)은 전부 **의자·침대 생활** 환경의 연출 영상이다.
AI Hub 샘플도 병원 병실(침대)이다.

### 왜 문제인가
한국 노인 가정에서는 **바닥에 이불을 깔고 자고, 바닥에 앉아 TV 를 본다.**
이 모델의 `fallen` 정의는 "몸통 수평 + 바닥 근처" 다 — **정상적인 바닥 생활이 곧 fallen 이다.**
4번보다 심각하다. 4번은 침대라는 ROI 로 완화할 수 있지만, 바닥 생활은 방 전체가 ROI 다.

### 선택지
- **자세 전이 중심으로 전환**: "어떻게 바닥에 도달했나"(급격한 하강 = 낙상 vs 천천히 앉음 = 정상)를 핵심 특징으로.
  현재 규칙 기반 베이스라인의 `발목-엉덩이 감소` 가 이미 이 방향이다 (fall 0.736 vs normal 0.022).
- 한국 데이터 확보: AI Hub 본편(491GB, 해외 IP 차단으로 미확보) · ETRI-Activity3D(노인 100명, 관절만 20GB, 매핑 필요)
- **자체 촬영**: 좌식 생활 정상 장면 수 시간. 낙상 연출 없이 정상만 찍어도 4번·8번에 쓸 수 있다.

### 팀 결정
- 타깃 환경이 요양원(침대)인지 가정(좌식)인지 — **이게 데이터 전략을 가른다**
- 자체 촬영 가능 여부(장소·피험자·동의)

## 6. 새 환경에서 오경보가 1.5~4배 늘어난다

### 관찰 (이진 위험 기준, gru)
| 조건 | Recall | FPR |
|---|---|---|
| 피험자 교차 (5-fold) | 0.867 ± 0.066 | **0.112** ± 0.066 |
| 환경 교차 (leave-one-out 평균) | 0.832 | **0.205** |
| 환경 교차 — edf 를 test 로 | 0.841 | **0.388** |

### 왜 문제인가
서비스 배포는 항상 "학습에 없던 환경" 이다. **기대할 FPR 은 0.11 이 아니라 0.2~0.4 다.**
사람이 바뀌는 것보다 환경(카메라 위치·조명·해상도)이 바뀌는 것이 더 어렵다는 게 실측으로 확인됐다.

### 선택지
- 설치 후 **현장 캘리브레이션**: 첫 1~2일 정상 영상으로 임계값 자동 조정 (모델은 그대로)
- 카메라 설치 표준화 (높이·각도) — 변수를 줄인다
- 데이터셋 7종으로 늘려 환경 다양성 확보 (Drive 에 있음, 추출 미완)

### 팀 결정
- 현장 캘리브레이션 기간을 제품에 넣을지

## 7. 1인 전제

### 관찰
가장 큰 바운딩 박스 한 명만 추적한다. 학습 데이터가 1인 클립이라 모델도 1인 전제다.

### 왜 문제인가
요양원 다인실, 보호자·요양보호사 방문, 부부 가정 — **2인 이상은 흔하다.**
보호자가 다가오면 "가장 큰 박스" 가 보호자로 바뀌어 낙상자를 놓친다.

### 선택지
- ByteTrack 으로 사람별 ID 유지 + 사람별 상태 머신
- ID 별 ring buffer (메모리 N배)
- "누가 넘어졌나" 까지 필요하면 얼굴/재식별 — 프라이버시와 충돌

### 팀 결정
- 1차 타깃을 독거(1인) 로 한정할지

## 8. "클립당 FPR" 은 서비스 지표가 아니다

### 관찰
지금 지표는 전부 **2~10초 클립 단위**다. FPR 0.112 는 "정상 클립 100개 중 11개를 위험으로" 라는 뜻이다.
서비스에서 판정은 0.5초마다 일어난다 — 하루 172,800회.

### 왜 문제인가
클립 FPR 을 그대로 두면 **하루 수천 번** 위험 판정이 난다. 지속 시간 규칙(R1)이 대부분 걸러내지만
**얼마나 걸러내는지 측정한 적이 없다.** 보호자가 견딜 수 있는 건 하루 1~2회다.

필요한 지표인데 없는 것:
- **시간당 오경보 횟수** (per-hour false alert rate) — 긴 정상 영상 필요
- **long-lie Recall** — 낙상 후 오래 누운 영상 필요 (현재 0개)
- 감지 지연 분포 (현재 3건: +0.15 / +0.5 / +0.5초)

### 선택지
- 정상 생활 영상 **수 시간** 확보 (자체 촬영·Toyota Smarthome untrimmed) → 시간당 오경보 측정
- 낙상 후 수 분 누운 연출 영상 소량 → t_fallen 검증
- 기존 `events.jsonl` 로 규칙 변형을 오프라인 재생 → 규칙 튜닝은 재촬영 없이 가능

### 팀 결정
- 평가 영상 확보 방법 (5번 자체 촬영과 묶어서)
- 목표 수치: 시간당 오경보 ≤ ? · 낙상 Recall ≥ ?

---

## 9. 실시간 입력·장비·비용

### 관찰
M3 MPS 에서 4K → 960 축소, **23~30 FPS**. 입력은 영상 **파일**만 (RTSP 스트림·웹캠 미구현).

### 왜 문제인가
- 실제 카메라는 RTSP/ONVIF 스트림이다. 끊김·재연결·지연 처리가 없다.
- 카메라 N대면 GPU N배. 엣지(Jetson·RPi)로 가면 YOLOv11n 도 10 FPS 이하일 수 있다.
- 클라우드로 보내면 영상 전송 = 프라이버시(10번) 문제.

### 선택지
- **엣지에서 키포인트만 추출, 서버로는 좌표만 전송** — 대역폭 1/1000, 영상이 밖으로 안 나간다
- YOLOv11n 을 ONNX/CoreML/TensorRT 로 변환해 장비별 벤치마크
- 카메라당 처리 주기를 낮춘다 (매 프레임 → 10fps 로 샘플링) — 낙상은 1초 사건이라 10fps 로 충분할 가능성

### 팀 결정
- 배포 형태: 엣지 / 로컬 서버 / 클라우드

## 10. 프라이버시·법규

### 관찰
침실·화장실은 낙상이 가장 많은 곳이자 카메라가 가장 부담스러운 곳이다.
현재 파이프라인은 영상을 저장하지 않고도 동작한다 — **키포인트(17점 좌표)만 있으면 판정·기록이 된다.**

### 왜 문제인가
- 가정: 본인·가족 동의 범위, 영상 보관 여부
- 요양원: CCTV 설치·열람 관련 규정이 있다 (구체 조항은 법률 검토 필요 — 여기서 단정하지 않는다)
- 알림에 스냅샷을 붙이면 유용하지만 영상 반출이 된다

### 선택지
- **기본을 "영상 미저장, 골격만 저장"** 으로. 이 구조의 장점을 제품 메시지로 쓸 수 있다
- 알림 스냅샷은 골격 오버레이만(원본 블러) 옵션
- 화장실은 카메라 대신 다른 센서(레이더·바닥 압력) — 범위 밖이지만 논의 필요

### 팀 결정
- 영상 저장 정책
- 법률 검토 담당

## 11. 기술 부채

- **임계값이 4장면에 맞춰져 있다** — `thr 0.5 / thr_exit 0.35 / min_det 0.5 / t_fallen 3 / eps 0.02` 전부 AI Hub 샘플 4개로 정했다.
- **테스트 코드 없음.** `pipeline_core.normalize()` 의 카메라 불변성은 수동 검증만 했다. 회귀 테스트로 고정할 가치가 있다.
- `extract_keypoints.py` 에 `normalize()` 복사본이 남아 있다 (Colab 단독 업로드용). 둘이 갈라지면 학습·추론 좌표가 어긋난다.
- **데이터 확장 미완** — 4개 데이터셋 + 합성 12k 가 Drive 에 있으나 Colab 세션 회수 8회로 추출 못 했다. GCP/로컬로 옮기면 하루 작업.
- `fall` vs `fallen` 라벨 경계가 흐리다 — 모델도 헷갈리고 규칙도 둘을 합쳐 본다. 3클래스가 맞는지, 2클래스(정상/위험) + 별도 "지속" 이 맞는지 재검토.
- GRU 는 64프레임 리샘플로 **지속 시간 정보를 의도적으로 버린다** (클립 길이가 단서가 되지 않게). 시간은 규칙이 센다. 이 분업이 맞는지 — 모델이 시간을 보게 하는 대안(고정 fps 윈도우)도 있다.
